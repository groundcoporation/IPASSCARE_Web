# 2026-09 수업·이용권·청구 정합성 정리

작성일: 2026-09-04  
대상: 학생관리, 수납관리, 앱 이용권, 월별 청구 계획

## 1. 문제 요약

학생관리에서 이번 달 수업·이용권을 변경했을 때, 앱의 실제 수업 일정과 수납관리의 청구 대상이 서로 다른 경로로 저장·조회되고 있었습니다. 그 결과 다음 문제가 함께 발생했습니다.

- 학생관리에서 수업 시간을 바꿔도 앱 일정에 즉시 반영되지 않는 경우
- 앱에는 활성 이용권이 있는데 수납관리에는 `청구 예정` 또는 `미청구`로 보이는 경우
- 청구서 또는 앱 이용권이 이미 존재하는 달에 학생관리에서 이용권을 다시 저장하면 계획 행이 중복되는 경우
- 부모 명의 가족 공용 차량 이용권과 자녀 명의 차량 이용권이 동시에 청구 대상으로 나타나는 경우
- 이번 달 이용권·청구 계획이 없는 재원생이 수납관리 목록에서 아예 누락되는 경우
- 실제 활성 이용권의 옵션과 학생관리의 이번 달 청구 계획 옵션이 다른 경우

## 2. 데이터 구조와 역할

| 데이터 | 역할 | 기준 |
| --- | --- | --- |
| `student_schedule_assignments` | 앱에서 사용하는 실제 수업 일정 | 앱 일정의 기준 데이터 |
| `academy_student_monthly_plans` | 학생관리에서 관리하는 월별 수업·청구 계획 | 수납관리의 청구 지시 데이터 |
| `user_packages` | 앱에 실제 지급된 이용권 | 이용권 보유·갱신 완료 판단 기준 |
| `academy_bills` | 생성된 청구서 | 청구서 발행·수납 상태 기준 |
| `class_schedules` | 지점별 개설 수업 시간표 | 선택 가능한 수업 목록 |

## 3. 발생 원인

### 3.1 수업 변경 RPC가 웹과 앱에서 달랐음

웹 학생관리와 앱이 각각 수업 변경 로직을 갖고 있어, 한쪽에서만 `student_schedule_assignments`를 갱신하거나 월별 계획만 수정하는 상황이 생겼습니다.

### 3.2 실제 이용권과 월별 계획의 상태가 분리되어 있었음

앱 이용권이 이미 `active`여도 같은 옵션의 `academy_student_monthly_plans`가 `planned`로 남아 있었습니다. 이 경우 수납관리에서 이미 갱신된 이용권이 다시 청구 후보가 될 수 있었습니다.

### 3.3 확정된 청구 구성도 학생관리 저장에서 삭제·재생성했음

기존 웹 저장 로직은 이번 달 이용권 계획을 넓게 삭제한 뒤 선택값을 다시 넣는 방식이었습니다. 이미 청구서가 생성되었거나 이용권이 지급된 계획까지 초안처럼 취급할 위험이 있었습니다.

### 3.4 수납관리의 표시 기준이 여러 개였음

수납관리는 앱 이용권, 월별 계획, 가족 공용 차량권을 병합해 표시합니다. 이때 다음 문제가 있었습니다.

- `applied` 계획을 조회 필드에서 제외하거나 상태 컬럼을 가져오지 않아 청구서가 있어도 `청구 대상 없음`으로 표시
- 학생관리 계획의 옵션과 실제 앱 이용권 옵션이 다르면 실제 이용권이 숨겨질 수 있음
- 지난달 가족 공용 차량권을 이번 달 갱신 후보로 잡아, 자녀 명의 차량 이용권과 이중으로 표시
- 이용권·계획·청구서가 전혀 없는 재원생은 목록에서 누락

## 4. 적용한 DB 마이그레이션

### 4.1 수업 저장 로직 통일

적용 순서:

1. 앱 `202609030002_unify_current_month_child_schedule.sql`
2. 앱 `202609030003_unify_current_month_child_schedule_package.sql`
3. 웹 `202609030004_use_shared_current_month_schedule_rpc.sql`

효과:

- 웹 학생관리와 앱이 같은 현재 달 수업 변경 로직을 사용
- 이번 달 수업 일정은 실제 앱 일정에 반영
- `다음 달에도 같은 수업 시간표 적용` 선택 시 다음 달 일정도 함께 반영
- 이용권·청구 계획은 수업 시간 변경만으로 임의 변경되지 않음

### 4.2 확정 청구 잠금 및 추가 청구 분리

파일: `supabase/migrations/202609040001_lock_current_month_billing_plans.sql`

효과:

- `academy_student_monthly_plans`에 `billing_source` (`standard` / `additional`)와 `origin_plan_id` 추가
- 이번 달에 청구서가 있거나 앱 이용권이 활성화됐거나 이미 `applied`인 이용권은 기본 청구 항목으로 수정·삭제 불가
- 실제 활성 이용권과 같은 `planned` 계획은 저장 시 `applied`로 승격
- 확정된 달에 새 금액을 더해야 하면 기존 항목을 수정하지 않고 `additional` 추가 청구로만 등록

### 4.3 9월 기존 데이터 복구

파일: `supabase/migrations/202609040002_reconcile_september_active_entitlements.sql`

이 파일은 구조 변경이 아니라 **2026년 9월 데이터만 대상으로 하는 일회성 복구 SQL**입니다.

처리 대상:

1. 실제 활성 이용권과 동일한 `planned` 계획 → `applied`로 승격
2. 실제 이용권 옵션과 다른, 아직 청구서가 없는 `planned` 계획 → 실제 활성 이용권 옵션으로 교체
3. 실제 활성 이용권은 있으나 9월 계획이 없는 학생 → `applied` 계획 생성

보호 조건:

- `academy_bills` 청구서의 금액·상태를 수정하지 않음
- 청구서가 이미 생성된 옵션은 교체하지 않음
- 실제 앱 이용권을 삭제·지급하지 않음
- 가족 공용 차량권은 형제자매 전원에게 복제하지 않고 대표 학생 한 명에만 반영
- 테스트 자녀(`자녀%`) 제외

## 5. 웹 코드 수정 사항

### 5.1 학생관리 (`AdminStudentTab.tsx`)

- 이번 달 수업 저장 시 공통 수업 일정 RPC 호출
- 이번 달 청구 계획 저장은 `save_current_month_student_billing_draft` RPC 호출
- 청구서 발행·이용권 지급·`applied` 계획이 있는 달은 기존 기본 청구 이용권 입력을 잠금
- 잠긴 달에는 `추가 청구 등록`만 허용
- 잠긴 상태에서도 수업 시간 저장은 가능

### 5.2 수납관리 (`AdminBillingTab.tsx`)

- 재원생 전체를 기준으로 목록 생성
- 이번 달 대상이 없는 학생은 `청구 대상 없음`으로 표시
- 상단 통계 추가: 전체 재원생 / 청구 대상 없음 / 청구 예정 / 갱신 완료 / 청구 처리됨
- `planned`와 `applied` 월별 계획을 모두 조회
- 청구서가 있어 `applied`가 된 계획도 수납관리에서 누락되지 않게 수정
- 자녀 명의 이번 달 차량 이용권이 있으면, 같은 상품의 과거 가족 공용 차량권은 갱신 후보에서 제외
- 가족 공용 차량권은 대표 학생 한 명에게만 표시

## 6. 확인된 9월 데이터 불일치 유형

### 안전하게 자동 복구 가능한 유형

실제 활성 이용권과 월별 계획의 옵션이 같고, 계획 상태만 `planned`인 경우입니다.

예: 김가온, 김나연, 김도훈, 김시원, 김시환, 박선우, 박시준, 우도윤, 이언, 이정찬

복구 방식: 계획 상태를 `applied`로 변경합니다.

### 실제 이용권과 계획 옵션이 다른 유형

예: 최지훈, 윤성준

복구 방식: 청구서가 없는 `planned` 기본 계획에 한해 실제 활성 이용권 옵션으로 맞춥니다. 이미 청구서가 있으면 자동 교체하지 않고 확인이 필요합니다.

### 실제 이용권만 있고 이번 달 계획이 없는 유형

예: 공도현, 김다온, 이지환

복구 방식: 실제 활성 이용권과 같은 `applied` 월별 계획을 생성합니다.

## 7. 남은 작업 순서

### 필수

1. `202609040002_reconcile_september_active_entitlements.sql`을 Supabase SQL Editor에서 실행
2. 실행 결과 오류가 없었는지 확인
3. 웹 개발 서버를 새로고침해 수납관리 화면 확인
4. 아래 대표 학생을 우선 확인
   - 최지훈: 실제 취미반 이용권이 수납관리·학생관리와 일치하는지
   - 윤성준: 수업 + 차량 이용권이 각각 한 번씩만 표시되는지
   - 이정찬: 수업 + 가족 공용 차량 이용권이 모두 `갱신 완료`인지
   - 강은찬: 청구서가 있으면 `청구 대상 없음`이 아니라 청구 생성 상태로 보이는지

### 배포 전 검증

1. 학생관리에서 이번 달 수업 시간을 변경하고 앱 일정 확인
2. `다음 달에도 같은 수업 시간표 적용` 선택 후 다음 달 일정 확인
3. 앱 이용권이 이미 있는 학생은 기본 청구 이용권을 수정할 수 없는지 확인
4. 추가 금액은 `추가 청구`로만 등록되는지 확인
5. 학생관리의 이번 달 이용권 구성과 수납관리 항목 수·금액이 일치하는지 확인
6. 가족 공용 차량권과 자녀 차량권이 중복 청구되지 않는지 확인
7. 지점을 `전체 보기`로 바꿔도 학생 수정 화면에는 해당 학생 지점의 수업 시간표만 보이는지 확인

### 배포

- 웹: `AdminStudentTab.tsx`, `AdminBillingTab.tsx` 변경분 배포
- 앱: 공통 수업 저장 RPC를 사용하도록 변경된 관리자 화면 배포
- 배포 전 `npm run build` 완료 확인

## 8. 운영 원칙

- 실제 활성 이용권은 해당 월의 갱신·보유 여부를 판단하는 최우선 근거로 사용
- 청구서가 생성되거나 이용권이 지급된 기본 청구 항목은 수정하지 않음
- 추가 비용은 기존 항목 수정이 아니라 추가 청구 행으로 남김
- 수업 일정과 이용권·청구 계획은 역할이 다르므로, 수업 시간 변경만으로 이용권을 자동 변경하지 않음
- 데이터 복구 SQL은 대상 월과 보호 조건을 명시한 일회성 SQL로 작성하고, 실행 전 조회 결과를 보관
