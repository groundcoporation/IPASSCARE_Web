# 유지보수 리팩토링 안내

현재 경로는 [페이지 중심 구조 안내](page-structure.md)를 기준으로 한다. 아래 1~12차 기록의 `features`·`components/admin` 경로는 당시 작업 이력이며, 현재는 `pages/admin`으로 이동했다.

## 작업 원칙

- 기준: `main`에서 분기한 `refactor/admin-maintainability`.
- 기존 테스터 작업과 분리한다. 운영 DB 변경·배포·SQL 실행은 포함하지 않는다.
- 화면과 업무 규칙을 유지하며 조회 → 저장 순서로 작은 단위씩 분리한다.
- 기존 마이그레이션은 적용 이력을 확인하기 전까지 이름 변경·합치기·삭제하지 않는다.

## 새 담당자가 볼 위치

| 위치 | 역할 / 주의점 |

## SQL 정리 기준

1. 마이그레이션, 조회 감사, 테스트, 일회성 보정으로 구분한다.
2. 적용 대상·선행 함수·트랜잭션·롤백·검증 쿼리를 확인한다.
3. 원격 적용 이력과 앱 저장소의 의존성을 대조한다.
4. 확인된 파일만 후속 단계에서 이동한다. 일괄 실행하지 않는다.

현재 웹의 `supabase/migrations`에는 29개 파일이 있다. 다음 두 파일은 버전이 겹친다.

- `202609030001_ensure_monthly_assigned_reservations.sql`
- `202609030001_sync_current_month_student_schedules.sql`

원격 적용 이력은 확인하지 않았다. 임의로 번호를 바꾸지 않는다.
`scratch`에는 DB 조사뿐 아니라 이관·시드·동기화 스크립트도 있으므로 읽기 전용이라고 가정하지 않는다.

| --- | --- | --- |

| 4 | 학습일지 조회 분리 | 서비스 추출, 조회 실패 시 전체 목록 정리, 오래된 응답 무시, 모의 테스트 |
| 5 | 학생관리 조회·수정 분리 | 목록·상세·탈퇴 이력 조회, 학생 저장, 청구 계획, 탈퇴/환불 기록 분리. Excel 경로·실제 화면 검수는 남음 |

| 7 | AdminPage 축소·인수인계 | 다음 작업. 실제 화면 검수 후 불필요 코드 정리 |

## 상담일지 수동 검수 항목

- 지점 전환, 학생 선택, 새로고침, 빈 목록, 조회 실패 안내.
- 학생 선택만 바꿀 때 전체 자료를 다시 조회하지 않아야 한다.
- 빠른 지점 전환 시 이전 응답이 최신 화면을 덮어쓰지 않아야 한다.
- 저장·삭제·공개·알림은 기존 경로를 유지한다. 실제 전송 검증은 격리 환경에서만 한다.
- 모의 테스트는 실제 권한·스키마·화면 검수를 대신하지 않는다.

## 학습일지 수동 검수 항목

- 특정 지점 / 전체 지점에서 원생·담당자·일지 표시 범위가 기존과 같은지 확인한다.
- 앱 연결 학생의 활성 수업과 수동 등록 학생의 웹 배정 수업이 각각 유지되는지 확인한다.
- 기존 반 전체 일지가 기존 기록 영역에 남는지 확인한다.
- 새로고침 시 기존 원생 선택은 유지하고, 현재 목록에 없으면 첫 원생을 선택한다.
- 빠른 지점 전환·새로고침·탭 이탈 후 이전 응답이 최신 목록을 덮어쓰거나 불필요한 오류 안내를 표시하지 않아야 한다.
- 조회 실패 시 학생·담당자·일지·선택 값이 함께 초기화되고 공통 오류 코드로 안내되어야 한다.
- 저장·수정·삭제·학부모 공개·알림·Excel 내보내기 경로는 이번에 변경하지 않았다. 실제 동작은 격리된 검수 환경에서 확인한다.

학습·상담 조회 서비스는 읽는 필드와 병렬 조회 방식이 달라 개별 파일을 유지한다.
공유 수업 배정 조회만 기존 공통 함수를 사용하며, 저장 로직을 함께 이동하거나 일괄 공통화하지 않는다.

앱·웹 공통 오류 카탈로그 동기화 테스트는 시작 시점부터 실패했다.
1~2차에서는 오류 코드를 추가하지 않았다. 이후 단계에서 추가하는 코드 항목은 개별 동기화하되, 두 저장소 전체의 기존 변경 이력 비교는 별도로 필요하다.

## 1차 검증 기록 (2026-11-25)

- 상담 조회·화면 콜백·환경·출결 회귀 테스트: 23개 통과. 실제 DB 연결 없이 모의 데이터 사용.
- `build:local`: 검증용 공개 설정으로 빌드 성공. 실제 서비스 연결·배포는 하지 않음.
- `lint`: 오류 없이 종료했으나 기존 경고가 남음.
- TypeScript 전체 검사: 기준 코드와 변경 코드 모두 48개 오류, 새 오류 없음. 기준 코드의 상담 컴포넌트를 메모리에서 대입해 진단을 비교함. 주로 미사용 선언 및 `main.tsx`의 type-only import 문제이며 별도 정리 필요.
- 기존 빌드 경고: 큰 번들 및 ExcelJS 정적/동적 import 혼용. 기능 분리 후 별도 최적화 대상.
- 실제 브라우저 화면·저장·권한 테스트는 미진행. 운영 반영 완료를 의미하지 않음.

## 2차 검증 기록 (2026-11-25)

- 학습일지 조회를 `studyData.ts`로 분리했다. 조회 컬럼·지점 조건·정렬·병렬 조회·활성 수업 조회 방식은 유지했다.
- 조회 실패 시 기존 담당자 목록과 학생 선택 값도 초기화한다. 이전 요청의 성공·실패 응답은 새 요청 결과에 반영하지 않는다.
- 학생 선택 보존, 빈 결과, 수동 수업 배정, 기존 반 전체 일지, 권한 오류, 조회 reject, 늦은 응답, effect cleanup 테스트를 추가했다.
- 기존 브라우저 환경 테스트의 기본 dev 기대값도 1차 변경에 맞춰 development로 수정했다. 운영 명령 분리 검증은 유지한다.
- 학습·상담 조회 테스트 24개 통과. 환경·출결·수납 계산/ID 보존·소개 페이지를 포함한 관련 회귀 테스트는 58개 통과했다.
- `build:local` 성공. 검증용 공개 설정만 사용했고 실제 DB를 연결하거나 키 파일을 생성하지 않았다.
- `lint`는 오류 없이 종료했다. 기존 경고는 남아 있다.
- TypeScript 진단을 원래 두 일지 컴포넌트와 비교한 결과 기준/변경 모두 48개 오류이며 새 오류는 없다.
- 기존 오류 카탈로그 동기화 실패는 미해결이다. 관련 58개 테스트 통과가 전체 저장소 검증 통과를 뜻하지 않는다.
- 실제 브라우저·DB 권한·저장·알림 테스트는 미진행이다. DB 변경·배포·커밋·푸시는 하지 않았다.
- 다음 작업은 학생관리 조회 경로부터 분리한다. 수정·탈퇴·이용권 저장 로직은 조회 검증 후 별도 단위로 진행한다.

## 3차 검증 기록 (2026-11-25)

- 학생 명부와 수업·상품 옵션·미등록 회원·활성 이용권 조회를 `src/features/students/services/studentData.ts`로 분리했다. 화면 데이터 타입은 같은 기능 폴더의 `types.ts`로 이동했다.

- 최신 요청만 화면에 반영하고, 지점 전환·화면 이탈 이후 이전 응답은 무시한다.

- 전체 오류 카탈로그 동기화 테스트는 다시 실행했으며 기존 불일치로 계속 실패한다(오류 처리 테스트 6개 통과, 전체 동기화 1개 실패). 새 코드 항목이 일치한다고 전체 계약이 동기화된 것은 아니다.
- 실제 DB·브라우저·권한 검수는 미진행이다. 운영 DB, main 브랜치, 기존 테스터 코드는 변경하지 않았다. 커밋·푸시·배포도 하지 않았다.

## 4차 검증 기록 (2026-11-25)

- 탈퇴 이력·환불 정보 조회를 `src/features/students/services/withdrawalData.ts`로 분리했다. `WithdrawalRecord`는 기능 폴더의 `types.ts`로 이동하고 기존 화면의 타입 export 경로도 유지했다.

- 실제 저장된 환불 금액·상태·메모·지급일은 그대로 반환한다. 복원 행은 DB에 쓰지 않는다. 환불 처리·탈퇴 처리·재원생 목록·화면 디자인은 변경하지 않았다.
- 조회 실패 시 오래된 이력을 지우고 공통 오류로 안내한다. 재원생 조회와 별도의 요청 번호 및 effect cleanup으로 늦은 성공/실패 응답을 무시한다.
- `WITHDRAWAL_LOAD_FAILED`를 앱·웹 오류 메시지에 같은 내용으로 추가했다. 새 항목 동기화 테스트 통과. 기존 앱 변경은 유지했다.
- 탈퇴 조회/변환/화면 콜백 테스트 21개 추가, 학생관리 테스트는 총 40개 통과. 기존 관련 회귀 항목 포함 98개 테스트 통과.
- 로컬 빌드 성공, lint 오류 없음(기존 경고 유지). TypeScript 기준/변경 모두 48개 오류로 새 오류 없음.
- 전체 오류 계약 테스트는 6개 통과, 기존 전체 카탈로그 동기화 1개 실패 상태를 재확인했다. 전체 테스트/타입 검사가 모두 통과한 것은 아니다.
- 실제 DB·브라우저 검수는 하지 않았다. 운영 DB, main, 기존 테스터 코드는 변경하지 않았고 커밋·푸시·배포도 하지 않았다.
