## 설치안에 반드시 포함할 내용

**Develop 현황 주의:** 2026-11-23 읽기 전용 메타데이터 검사에서 `point_logs` RLS 비활성, 정책 0개, 익명 SELECT/INSERT 권한을 확인했다. 실제 내역은 읽지 않았다. 수정 후보는 로컬에서만 검증했으므로 현재 Develop의 익명 권한이 해결된 것은 아니다. 운영 DB까지 동일하다고 추정하지 않는다.

1. 대상은 `IPASSCARE-develop`으로 고정하고 프로젝트 식별자·실제 호스트·고객 데이터 유무를 재확인한다. 일반 `--linked db push`로 운영에 적용하지 않는다.
2. 적용 전 함수 정의·ACL·정책·트리거 및 가상 데이터의 복구 지점을 확보한다. 테스터 이력은 후속 설치에서 비우지 않는다.
3. 현재 웹에 필요한 미적용 SQL을 검토한다. 로컬에서 함께 검증한 파일은 다음과 같다.
   - `202611170002_register_manual_ledger_attendance.sql`
   - `202611170003_harden_journal_and_app_bill_permissions.sql`
   - `202611170004_archive_academy_student.sql`
   - `202611200001_fix_offline_partial_cancellation_status.sql`
4. 원본 출결·탈퇴 함수만 설치하면 테스터 검증이 빠진다. 테스터 스키마/이력·RLS·RPC 보호·가상 발송·멱등 지급 wrapper·Storage 정책을 조합한 설치 순서를 검증한다. hardening 후에는 새 함수 정의에 보호를 적용하고 구형 캐시 정의로 되돌리지 않는다.
   - 포인트 RLS 후보와 `tester-point-trigger-guards.mjs`의 두 트리거 보호도 함께 적용·검증해야 한다. 스키마 생성 후 보호를 설치하며, 정의 해시가 다르면 중단한다. 코어 SQL만 단독 적용하는 것은 충분하지 않다.
5. 서버가 관리하는 metadata로 가상 지점과 계정을 연결한다. 원생·연락처·푸시 토큰·결제 데이터는 전부 합성 데이터만 사용한다. 설치 전 이미 표식이 제거된 계정은 현재 metadata만으로 식별할 수 없으므로 별도 확인한다.
6. 실패 시 먼저 테스트 로그인을 닫고 세션 접근을 차단한다. 비공개 이력을 삭제하거나 RLS를 끄는 방식으로 복구하지 않는다. 승인된 백업/정의로 복구한 후 재검증한다.

## 현재 의도적으로 막은 동작

실제 결제·환불·문자·푸시는 운영으로 우회하지 않는다. 가상 처리 또는 차단 안내를 사용한다. 앱 전용 포인트 이벤트, 계정 자체 탈퇴, 검토되지 않은 일괄 예약 두 경로도 테스터에게는 차단한다. 따라서 현재 상태를 ‘앱·웹의 모든 기능을 제한 없이 체험 가능’으로 안내하면 안 된다.
