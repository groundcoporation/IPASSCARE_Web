# 실제 관리자 웹의 테스트 로그인

테스터는 별도 Preview 호스트의 `/tester`에서 로그인한다. 로그인 이후에는 운영과 같은 `AdminPage` 및 동일한 출결·수납·일지·셔틀 메뉴와 DB 호출을 사용한다. Preview의 가상 지점에 저장되므로 새로고침 후에도 테스트 기록이 남는다. 원장 계정에 허용된 화면을 기준으로 하며 최고 관리자 전용 화면은 열리지 않는다.

## 공개하기 전 안전 확인

체험 호스트는 운영과 다른 Supabase Auth·DB·Storage로 고정한다. **운영 원생·보호자·전화번호·결제정보·푸시 토큰을 복제하지 않는다.** 기존 Develop 테스트 지점을 쓴다면 가상 데이터 외의 고객 데이터가 테스터 권한으로 조회되지 않는지도 점검한다.

테스트 웹은 Preview Supabase의 Auth·REST·Storage를 허용하며 브라우저의 Edge Function 호출을 차단한다. 직접 호출하는 문자 중계와 KSNET 결제 경로도 Preview에서는 차단한다. 이 브라우저 차단은 서버 설정을 대체하지 않는다.

- Preview의 운영 PG·환불·문자·푸시 자격 증명과 실제 접속 주소를 제거한다. 별도 샌드박스나 스텁이 필요한 경우 운영으로 우회할 수 없어야 한다.
- 자동청구·미납알림 등 Preview의 cron, SQL 트리거 및 DB 웹훅, 호출 가능한 Edge Function도 검토한다. 실제 외부 발송 경로가 남아 있으면 테스트 로그인 진입을 활성화하지 않는다.
- 운영 지점·다른 가상 지점 조회/변경이 SQL RLS와 RPC 권한으로 차단되는지 검증한다. 브라우저 지점 필터만으로는 부족하다.
- 현장 수납 기록과 출석 등록·취소는 Preview DB에 실제로 저장한다. 앱 청구 발송·푸시·환불 등 외부 연동은 차단 상태다. 이 경로까지 체험하려면 테스트 전용 서버 연동을 별도로 준비한다.

### 현재 공개 보류

#### 2026-11-23 현재 결과: 로컬 포털·서버 호출 격리 검증

- **실제 로컬 웹·Auth·DB E2E 162개 통과**, 관련 회귀/환경 테스트 **99개 통과**. Preview/운영 빌드 모두 성공했다. 기존 ExcelJS 정적·동적 import 혼용 및 큰 번들 경고는 남아 있다.
- 권한 회수 후 기존 JWT뿐 아니라 토큰 갱신과 새 로그인으로 발급받은 JWT에서도 출결 등록/취소와 추가 관리 RPC 호출이 거부됐다. 원생 목록은 숨겨지고 출결 차감 상태는 보존됐다. 서버 전용 테스터 이력 테이블이 Auth metadata 삭제 후에도 동작함을 확인했다.
- 보호 규칙 후보는 **60개 시그니처**다. 청구 생성/무료 처리/삭제/구성 변경, 현장결제 예정 취소, 보강·예약 생성·수업 배정·키패드·셔틀 처리·학생 탈퇴 경로를 추가했다. 다른 지점 ID와 위조 청구 연결을 거부하고 자기 지점의 앱 직접 청구 삭제는 허용되는 것을 확인했다. 모든 기능의 정상/예외/동시성 조합을 완전히 검사했다는 뜻은 아니다.
- 앱 전용 포인트 이벤트·계정 자체 탈퇴·일괄 예약 2개 경로는 테스터 호출을 명시적으로 차단했다. 현재 웹에서 직접 사용하지 않는 경로이며, 검토된 가상 구현 없이 허용하지 않는다. 캐시의 일괄 예약 두 함수는 서로 다시 호출하는 구조여서 별도 검토가 필요하다. 운영 함수를 수정한 것은 아니다.
- `tester-rpc-inventory.mjs --cached`로 캐시 public 함수 98개를 분류했다. 보호 후보 57개, 읽기 전용 helper 6개(정의 해시 고정), 별도 트리거 검토 23개, 서버 전용 12개다. 캐시에 없는 수동 출결/학생 탈퇴 보호 후보가 2개이고, 보호 Map에는 서버 전용 의존 함수도 포함돼 총합이 단순 합산과 다르다. 직접 호출 함수의 미분류는 0개지만 **트리거 부작용과 서비스 역할 호출의 안전성까지 완료된 것은 아니다.**
- 실제 `PreviewAdminEntry` 로그인 폼을 로컬 Preview 환경 분기로 실행해 일반 계정 거부, 테스터 로그인, 자기 지점 원생 표시/타 지점 숨김, 새로고침 세션 복구, 서버 표식 회수 후 로그인 화면 복귀를 검증했다. 응답 모킹은 없지만 Supabase 대상은 loopback Docker다. 실제 호스팅된 Develop Preview 검증이나 빌드 환경 검증 완화로 해석하지 않는다.
- 전체 학생 목록 검사에서 캐시 Develop 스키마의 `archived_at` 누락을 발견했다. 임시 DB에 기존 `202611170003_harden_journal_and_app_bill_permissions.sql` 및 `202611170004_archive_academy_student.sql`을 함께 적용했다. hardening으로 교체된 앱 청구 삭제 함수를 구형 캐시 정의로 덮어쓰지 않고 새 정의에 테스터 검증을 다시 적용했다. 탈퇴 함수도 생성 시점에 보호한다. 두 migration의 클라우드 적용 여부는 별도 확인해야 한다.
- Develop 읽기 전용 재점검: 배포 Edge Function 0개, 활성 cron 0개, 네트워크 트리거/공개 SQL 외부 호출 0개, 결제·문자·푸시 통합 Secret 이름 미발견. Secret 값은 읽지 않았고 Auth Hook은 미검증이다. 이 결과만으로 공개를 허용하지 않는다.
- 임시 스택·볼륨·네트워크는 정리했고 기존 `ipasscare-local-test` DB는 유지했다. 운영·Develop 클라우드 쓰기·main·원격 반영은 하지 않았다. 공개 플래그는 계속 false다.
- 남은 단계와 적용 전 확인 사항은 `environments/tester-rollout-checklist.md`를 따른다. 후보 SQL의 마지막 `rollback`을 `commit`으로 바꾸거나 보호 없는 원본 RPC만 단독 적용하지 않는다.

#### 2026-11-23 이전 검사 기록: 새 토큰 권한 회수 보완 — 아래 대기는 위 결과로 해소

- 기존 후보는 서버 표식과 JWT 표식이 모두 사라지면 일반 사용자 호환 경로(`*`)로 분류할 수 있었다. 프로필이 활성 원장으로 남은 상태에서 토큰 갱신·재로그인 시 적용될 수 있는 경로로, 코드 검토에서 확인했다. 이번에는 Docker 엔진 미실행으로 실제 재현/수정 후 E2E는 실행하지 못했다.
- 비공개 `tester_identities` 테이블에 테스터 계정 ID만 보관하는 후보를 추가했다. 적용 시 기존 서버 표식을 수집하고, 이후 Auth 계정 생성/metadata 변경 시 서버 트리거로 이력을 남긴다. 클라이언트의 테이블 접근 권한은 없으며 표식 제거만으로 이력이 삭제되지 않는다. 일반 계정을 가상 지점 소속만으로 테스터로 분류하지 않는다.
- 테스터 이력이 있지만 현재 서버 표식이 없으면 `core_scope()`는 접근 불가를 반환하고 `is_tester_actor()`는 계속 참을 반환한다. 기존 JWT 유무에 의존하지 않고 검토된 RPC 보호 경로와 직접 테이블 RLS를 유지하도록 했다. 현재 서버 표식을 명시적으로 다시 부여하면 기존 활성 상태/지점 검사를 거쳐 복구되며, 실제 Auth 계정 삭제 시 해당 이력도 삭제된다.
- 이 테이블은 롤백 전용 후보의 일부다. 실제 공개 전에는 **이력 보존·백업/복구·후속 배포 시 초기화 금지·기존에 표식이 제거된 계정 조사**를 포함한 설치 절차가 필요하다. 설치 전에 이미 표식이 제거된 계정은 현재 metadata만으로 식별할 수 없다. 전체 RPC 검토를 대체하지 않는다.
- 실제 E2E에 토큰 갱신과 로그아웃 후 재로그인 각각 5개 검사를 추가했다. 새 JWT에서 표식이 사라진 사실, 등록/취소 거부, 원생 목록 숨김, 잔여 횟수 불변을 검증하도록 했다. **이 신규 10개는 아직 미실행이며, 종전 72개 통과를 이번 수정본의 통과로 간주하지 않는다.** Docker 시작 후 전체 재실행이 필요하다.
- 관련 로컬 회귀 테스트 **87개 통과**, `git diff --check` 통과. 이 결과는 SQL의 실제 실행 및 Auth 트리거 동작 검증을 대신하지 않는다. Docker 사전 검사에서 엔진 파이프가 없어 중단했으며 임시 스택/가상 데이터는 생성되지 않았다.
- 운영·Develop 클라우드·main·원격 미반영이며 테스터 공개 플래그도 계속 비활성이다. 실제 앱/웹 실행 코드나 운영 migration은 변경하지 않았다.

#### 2026-11-20 후속: 테스터 표식 회수 후 출결 definer 우회 차단

- 실제 로컬 Auth에서 테스터로 로그인한 뒤 서버의 `ipasscare_tester`/`ipasscare_test_branch` 표식을 제거하고 기존 JWT로 출석 취소를 직접 호출했다. 기존 후보에서 취소 RPC가 서버 테스터 표식을 검사하지 않아 취소/횟수 복구가 가능한 것을 재현했다. 첫 검사는 `tester_revoked_attendance_cancel_denied`에서 실패했고 임시 스택은 정리했다. 운영에서 공격/데이터 변경을 실행한 것은 아니다.
- `cancel_attendance_ledger_entry`와 새로 설치하는 `register_manual_ledger_attendance`에 공통 테스터 preamble을 추가했다. 역할·지점뿐 아니라 서버 Auth 표식과 활성 프로필을 확인하며, 캐시된 JWT에 테스터 표식이 남았는데 서버 표식이 없으면 거부한다. 기존 자녀·이용권·예약 검증 및 일반 원장의 처리 로직은 보존한다.
- 수동 등록 함수는 캐시 DB 메타데이터에 없어 기존 메타데이터 기반 함수 패치 루프에서 빠질 수 있었다. `guardTesterManualAttendance`로 생성 시점에 보호하고, Develop 롤백 검사와 로컬 E2E 양쪽에서 같은 경로를 쓰도록 했다. 조기 `already_registered` 반환보다 먼저 검사한다. 원본 운영용 등록 migration 자체를 테스터 전용으로 변경하지 않았다.
- 보호 목록은 **총 36개 시그니처(임시로 설치하는 수동 등록 포함)**다. 기존 메타데이터 함수는 35개이고 새 수동 등록 후보가 1개다. 이는 전체 호출 가능 RPC 감사 완료를 뜻하지 않는다. 기존 등록 migration만 단독으로 테스터 환경에 적용하면 이번 보호가 빠지므로, 배포 시 공통 스키마/함수 보호와 조합한 적용 계획이 필요하다.
- **실제 E2E 8개 추가, 총 72개 통과.** 활성 테스터의 취소→재등록 정상 처리, 서버 표식 제거 후에도 JWT 내부에 이전 테스터 claim이 남아 있음을 확인, 기존 JWT로 등록/취소 모두 거부, 상태/잔여 횟수 불변, 계정 정지 후 등록/취소 거부를 검증했다. 같은 실행에서 일반 원장의 기존 출결·부분 수납·직원·일지 E2E도 통과했다.
- 관련 로컬 회귀 테스트 **85개 통과**. 이번 수정은 테스터 SQL 생성/검사 후보와 E2E 코드이며 앱/웹 실행 코드·운영 DB 함수는 변경하지 않았다. 임시 스택/볼륨/가상 데이터는 정리했고 기존 재현 DB는 유지했다. 운영·Develop 클라우드·main·원격은 미반영이다.
- 검사 범위는 기존 테스터 JWT다. 새 로그인/토큰 재발급·서버 권한 회수 운영 절차 및 나머지 definer RPC는 별도 검토 대상이다. 일반 사용자 호환 경로를 테스터 회수 정책으로 대신하지 않으며, 실제 권한 회수 시 프로필 역할/활성 상태와 Auth 정책도 함께 검토해야 한다. 공개 플래그는 계속 비활성이다.

#### 2026-11-20 후속: 실제 출결 장부 등록·취소 및 공용 API 반영

- 별도 Docker 스택에 전체 `AdminPage`를 띄워 출결관리→출결 조회(원생 장부) 메뉴 이동부터 검증했다. 로컬 전용 일반 가상 원장 계정(테스터 metadata 없음)으로 실제 Auth 로그인을 사용했다. 운영/Preview 테스터 진입 제한을 우회하거나 환경 검증 코드를 완화하지 않았다. 이 검사는 일반 원장의 출결 장부 흐름이며 `/tester` 포털 인증 E2E와 구분한다.

- 검증 전후 스키마·권한 메타데이터 SHA-256이 동일했다(`d266b950bc6f96d0a773ee4543e031e9551b1b9bbe51776e82746ead082e451e`). 운영 DB는 변경하지 않았다.
- **아직 공개 불가**: 정상 쓰기·타 지점 쓰기 차단, 나머지 테이블·RPC·Storage, 서버의 외부 결제·문자·푸시 및 자동 작업 검증이 남아 있다. 4개 테이블 조회 검사 통과를 전체 권한 분리 완료로 해석하지 않는다.

재검증 명령(웹 폴더, 연결 대상이 지정된 Develop일 때만 실행):

```powershell
node --test tests/testerAccess.test.mjs tests/testerPolicyCheck.test.mjs
node scripts/check-tester-preview.mjs
node scripts/check-tester-preview.mjs --run
```

마지막 명령만 임시 DB 검사를 실행한다. `--apply`는 없으며 운영 대상으로 실행할 수 없다. 실패 시 응답 원문을 출력하거나 자동 재시도하지 않는다.

공용 `IPASSCARE-develop`에서 테스트 원장 계정으로 검증했을 때, 자기 가상 지점뿐 아니라 다른 가상 지점 원생도 조회됐다. 검증에 사용한 원장 권한은 회수했다. 브라우저에 지점 필터가 표시돼도 DB 권한이 분리된 것은 아니다. 이 상태에서는 운영의 테스트 로그인 링크와 Preview 진입을 모두 꺼 둔다.

기존 `IPASSCARE-develop`을 체험 전용으로 전환한다. 기능 개발과 마이그레이션 테스트는 로컬 Docker에서 하고, 운영 DB는 배포 후 실제 동작 확인에만 제한적으로 사용한다. Develop에 운영 데이터를 복제하지 않는다. 테이블·RPC·Storage의 권한, 기존 테스트 계정 정리, 데이터 초기화 정책을 먼저 검증한다.

`supabase/checks/tester_preview_access_audit.sql`은 고객 데이터를 조회하지 않고 공개 스키마의 테이블 권한, 뷰 및 권한 상승 함수의 검토 범위를 집계한다. 결과만으로 공개를 승인하지 않는다. 실제 테스터 계정으로 자기 지점의 출결·현장 수납이 저장되는지, 다른 가상 지점이 조회·변경되지 않는지, 실제 발송·결제가 일어나지 않는지 별도로 확인한다.

`supabase/checks/tester_preview_core_policy.sql`은 원생, 출결 기록, 학원 원생 및 청구 테이블의 직접 접근을 지점으로 제한하는 정책 후보를 가상 지점 두 곳으로 검사한다. 전체가 롤백되는 검증이며 배포용 마이그레이션으로 실행하거나 공개 승인에 사용하지 않는다. 다른 테이블과 `SECURITY DEFINER` RPC, Storage는 별도 검토가 필요하다.

## 계정 및 배포 설정

1. 기존 `supabase/seeds/seed-develop-smoke.ps1`이 생성한 가상 지점(예: `devsmoke-<10자리 hex>-1`)을 확인한다. 무작위 실 지점을 할당하지 않는다.
2. **Preview 프로젝트 Auth**의 테스트 계정과 **같은 UUID인** `public.users` 프로필을 가상 지점의 활성 원장(`role=director`)으로 준비한다. 이미 발급한 시뮬레이션 계정은 프로필 연결 전까지 실제 관리자 화면을 열 수 없다. 운영 역할은 변경하지 않는다.
3. Preview용 [Supabase Auth Admin API](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid)로 계정의 기존 `app_metadata`를 보존하면서 `ipasscare_tester: true`와 `ipasscare_test_branch: "<가상 지점 ID>"`를 함께 설정한다. 둘째 값은 프로필의 `branch_id`와 정확히 같아야 한다. `user_metadata`로는 권한을 받을 수 없다. 관리자 키는 서버에서만 사용한다.
4. 위 안전 검증이 끝나면 **Preview** 빌드에만 `VITE_TESTER_ISOLATION_VERIFIED=true`를 설정하고 `npm run build:preview`로 별도 호스트에 배포한다. 기본값은 꺼짐이다. 켜진 빌드는 지정된 `IPASSCARE-develop` 프로젝트만 허용하며, 운영이나 다른 프로젝트를 대상으로 빌드하면 설정 오류가 난다. 로컬 Preview 확인은 `npm run dev:preview`.
5. **운영** 빌드의 `VITE_TESTER_PREVIEW_URL`에 승인된 별도 Preview HTTPS 주소를 설정한다. 운영 관리자 로그인에 **테스트 로그인** 링크가 보이고 Preview `/tester`로 이동한다. 설정하지 않으면 운영 로그인은 그대로다.

운영 호스트의 `/tester`는 활성화되지 않는다. 테스트 로그인은 운영으로 보내지거나 운영 세션을 공유하지 않는다. 테스트가 끝나면 Preview 계정을 비활성화하거나 권한을 제거한다.
