# 공지 기능 경계

## 조회

- `api/noticeReads.ts`는 일반/HQ 공지 타입과 읽기 전용 서비스를 제공한다. 기존 전체 필드 조회, 중요순·최신순 정렬, 일반 공지의 지점+전역 공지 조건을 유지한다.
- 명시적 null은 최고관리자의 전체 지점 조회다. 일반 화면은 지점 없는 일반 계정과 관리자 포털 대상이 아닌 역할을 조회 전에 차단한다. 필터에 삽입할 지점 ID는 영문/숫자/밑줄/하이픈만 허용해 조건 문법 주입을 막는다. 실제 권한은 서버 RLS가 최종 보장해야 한다.
- 모든 응답의 error와 목록/기초 표시 필드 형식을 검사한다. 조회 실패를 정상 빈 목록이나 고정 예시 공지로 바꾸지 않는다. 과거 HQ 오류 시의 공식 런칭 예시 공지는 제거했다. 정상 0건은 그대로 0건이다.
- 두 화면의 loader는 useCallback으로 안정화하고 effect는 loader를 의존한다. 새 요청 번호·현재 계정/지점 참조가 일치할 때만 목록/선택/로딩/오류를 반영한다. 이전 저장 콜백의 늦은 재조회도 새 계정/지점에서는 시작하지 않는다.
- effect 정리 시 이전 요청을 무효화하고 선택/작성창/일반 상세창을 닫는다. 실패 시 이전 목록과 선택을 비운다. 일반 상세는 현재 목록에 같은 ID가 있으면 최신 행으로 바꾸고, HQ는 같은 선택을 유지하거나 최신 목록의 첫 행을 선택한다. 선택 상태를 loader 의존성에 넣어 반복 조회하지 않는다.

## 검증과 미완료 항목

- `npm run test:notices`: DB/푸시 연결 없이 필터/오류/비정상 응답/지점 누락/계정 전환/선택 동기화/오류 카탈로그를 검증한다. 실제 브라우저·RLS·대량 행 페이지 처리 검수를 대체하지 않는다.
- 저장·삭제·푸시 요청은 아래 서비스로 분리했다. 실제 서버 권한·삭제 연쇄 영향·알림 수신·동시 기기 중복 방지는 별도 검증이 필요하다.
- 다른 기기 동시 편집·실제 운영 권한·전체 오류 카탈로그 불일치 등은 별도 검토 항목이다.

## 저장·삭제·푸시

- `model/noticeWrite.ts`는 제목/내용·UUID·역할·일반 계정의 원래/대상 지점 범위를 검사한다. 일반 계정이 전역/다른 지점 공지를 변경하는 클라이언트 경로를 차단하며 본사 공지는 admin만 변경한다. 실제 역할 판정/권한 보장은 서버가 담당한다.
- `api/noticeWrites.ts`는 auth.getUser의 error와 현재 사용자 ID 일치를 확인한 뒤 기존 insert/update/delete를 한 번 호출한다. 일반 공지 수정/삭제는 원래 branch_id도 조건에 포함한다. 저장은 반환 UUID/요청 필드, 삭제는 반환 UUID를 확인하며 select 권한/응답 미확인 때 자동 재시도·테이블 우회는 없다.
- 작성자 이름·배지와 일반 공지 표시 필드는 기존 흐름을 유지했다. 본사 공지는 고정 작성자와 생성시각을 유지하되 과거 로컬 headquarter_notices 스키마에 없는 branch_id를 저장하지 않는다. 운영 스키마 일치 여부는 별도 확인이며 스키마 변경은 하지 않았다.
- 푸시는 **새 일반 공지 + 사용자가 요청한 경우 + 저장 응답 확인 후**에만 기존 Edge를 한 번 호출한다. 수정/본사 공지에는 추가 발송하지 않는다. 성공 flag와 0 이상 안전 정수 카운트를 확인한다. 일부 실패/응답 유실은 저장 실패가 아니라 `NOTICE_PUSH_PARTIAL`이며 저장된 ID를 유지한다. 카운트는 요청 응답이지 기기 수신 보장이 아니다.
- 공지 저장이 확인됐으면 푸시 문제로 작성창을 유지하지 않는다. 창을 닫고 부분 결과를 안내한 뒤 목록을 조회한다. 저장/삭제 응답 미확인은 새 조회 전 재실행을 막으며, 후속 목록 실패는 `NOTICE_REFRESH_FAILED`로 구분한다. 자동 재발송/재저장/롤백은 없다.
- 두 화면 모두 저장/삭제 공통 ref 잠금·폼/닫기 보호·이전 조회 무효화·mount/계정/지점/편집 epoch 검사를 사용한다. 변경 중 일반 조회를 막고 변경 후 명시적 조회만 허용한다. 범위를 바꾼 경우 잠금 해제 후 최신 loader로 현재 목록을 읽고, 이탈 뒤에는 새 조회를 시작하지 않는다.
- 미확인 후에는 새로고침 또는 탭 재진입으로 실제 목록을 확인한 뒤 진행한다. 푸시를 요청한 저장이 이미 시작됐다면 화면 전환이 서버 저장/발송을 취소하지 않는다.
- 서버 RLS·반환 select·실제 삭제 영향·동시 편집/멱등성·Push Edge의 현재 배포/로그/권한은 미완료 검토 대상이다. 이번에 Edge/SQL은 수정하지 않았다. 프론트 중복 클릭 방지로 다중 기기 중복까지 막는 것은 아니다.
- `npm run test:notice-writes`: 실제 저장/발송 없는 auth·응답·부분 푸시·권한·중복/화면 전환·문구 동기화 테스트다.
