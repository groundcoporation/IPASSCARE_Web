# 수납 관리 기능 경계

## 현재 분리한 파일

- `api/paymentHistory.ts`: 결제 탭의 결제·연결 이용권·자녀·상품·문자 충전 기록 조회. 읽기 전용이며 관계 조회 전체가 정상 응답일 때만 결과를 반환한다.
- `model/paymentHistory.ts`: 결제 타입과 연결정보 조립, 한국시간 월 필터, 검색·상태·합계·환불 참고 계산, 결제 표시 문구를 공유한다. 화면과 엑셀의 표시 문구가 같은 함수를 사용한다.
- `types.ts`: 웹 청구서, 현장 수납 참고 정보, 앱 결제요청의 타입.
- `model/billingPeriod.ts`: 기존 월 시작/종료일 계산. 화면과 조회 서비스에서 공유한다.
- `api/billingReads.ts`: 청구내역과 앱 관리자 직접 청구 조회, 자동 청구 설정 조회. DB client를 전달받는 읽기 전용 서비스다.
- `api/billingTargets.ts`: 청구대상 계산에 필요한 학생·상품·계획·배정·보유권·기존 청구를 읽는다. 기존 조회 순서/필터를 유지하고 모두 성공했을 때만 계산 결과를 반환한다.
- `api/billingAutomation.ts`: 자동 청구 설정과 대상 학생의 기존 upsert 저장을 담당한다. 로그인 조회 오류와 반환 행을 확인하며 청구 생성/발송을 직접 호출하지 않는다.
- `model/billGeneration.ts`: 선택 대상·할인 입력을 기존 건별 RPC 매개변수로 바꾸는 순수 준비 함수. 화면과 공유하는 대상 선택 키도 정의한다.
- `api/billCreation.ts`: 기존 청구 생성 RPC를 건별로 한 번씩 실행하고 확인된 결과/미확인 결과/미실행 수를 집계한다.
- `api/billActions.ts`: 웹 청구서 삭제·앱 직접 청구 삭제·0원 무료 처리의 기존 RPC와 응답 확인. 직접 테이블 삭제·실결제·알림 발송은 수행하지 않는다.
- `api/billDelivery.ts`: 기존 Edge 함수의 청구서 앱 등록·납부 알림 요청과 항목별 결과 확인. 외부 호출은 한 번만 하며 자동 재발송하지 않는다.
- `api/offlinePayment.ts`: 청구서 수기 수납의 예정 등록과 기존 결제 확정. 청구서/앱 직접 결제의 응답 차이를 처리하며 두 화면에서 확정 계약을 공유한다.
- `api/offlineLedger.ts`: 별도 현장 수납 탭의 내역·자녀 정보 조회와 기존 결제 확정·예정/완료 취소. 화면은 입력·확인 창·로딩과 목록 반영만 관리한다.
- `api/billingPlan.ts`: 기본 청구 계획 교체·선택 월 추가 청구 등록·예정 추가 항목 삭제의 기존 RPC와 응답 확인.
- `model/billingPlan.ts`: 기본/전체 옵션 ID 추출과 상품 구성 중복 비교. 외부 연결이나 화면 상태를 변경하지 않는다.
- `model/paymentCancellation.ts`, `api/paymentCancellation.ts`: AdminPage의 카드 전체취소/현장 장부 취소 검사와 요청. 부분취소·이전 환불 이력·미지원 경로는 차단하며 브라우저 DB 취소 쓰기는 하지 않는다. 상세 한계는 `docs/payment-cancellation-safety.md`를 참고한다.
- `model/billingTargetCalculation.ts`: 조회 결과를 받아 명부·상품 옵션·청구대상·청구 상태를 계산하는 순수 함수. 화면 state나 DB에 접근하지 않는다.
- 화면: `src/pages/admin/billing/views/AdminBillingTab.tsx`.
- 테스트: `npm run test:billing`.

## 삭제·무료 처리 경계

- 웹 청구서는 `academy_bills.id`를 `p_bill_id`로 보낸다. 연결된 `payment_request_id`로 대체하지 않는다. 응답의 `success: true`와 동일한 `bill_id`를 확인한다.
- 앱 직접 청구는 `issued_source = admin_app`이며 기존 삭제 가능 상태일 때 `payment_requests.id`를 `p_request_id`로 보낸다. 동일한 `request_id` 응답을 확인한다. 연결 청구·실결제 여부와 지점 권한은 서버가 최종 검사한다.
- 무료 처리는 미납·0원·수납 0원·앱 미발송 항목만 요청한다. 신규 완료 응답은 결제/지급 이용권 UUID까지 확인하고, `already_completed: true`는 기존 완료 응답으로 인정한다.
- 쓰기는 자동 재시도하지 않는다. 응답 유실/형식 미확인은 실패 확정이 아니며 상태 재조회가 필요하다. RPC 오류를 직접 테이블 쓰기·삭제로 우회하지 않는다.
- 세 작업은 화면의 공통 busy 잠금을 사용한다. 작업이 진행 중이면 추가 확인 창과 중복 요청을 막는다.
- 완료 후 청구내역과 청구대상을 하나의 조회 번호로 묶어 갱신한다. 두 기존 loader를 병렬 호출해 서로 무효화시키지 않는다. 한쪽 조회 실패 시 전체 결과를 비우고 `BILL_ACTION_REFRESH_FAILED`로 완료된 변경과 조회 실패를 구분한다.
- 지점·월·탭 변경/화면 이탈 후 이전 요청은 새 화면의 목록·선택·로딩을 덮어쓰지 않는다. 이미 보낸 서버 요청 자체가 취소되는 것은 아니다.
- 실제 RPC 배포 상태·RLS·다른 탭 동시성·이미 발송된 앱 청구의 만료/삭제·무료 이용권 지급은 격리 환경에서 별도 검수해야 한다.

## 청구 계획 편집

- 기본 계획은 기존 `save_student_monthly_package_plan`에 학생 ID·월 1일·옵션 목록을 전달한다. 기본 항목만 교체하며 추가 항목/실제 지급권은 목록에 섞지 않는다. 빈 배열은 명시적 기본 계획 비우기다.
- 추가 청구는 기존 `add_student_additional_billing_plan`에 선택 월을 전달한다. 직접 추가와 기본 계획 잠금 후 추가 전환은 기존처럼 이번/다음 달만 허용하고 서버가 최종 검증한다.
- 기본 계획 잠금 오류의 별도 추가 청구 전환은 사용자 확인을 받은 경우만 실행한다. 결과 미확인·일반 오류·조회 실패에는 추가 청구로 자동 우회하지 않으며 이전 화면의 늦은 잠금 오류로 확인 창을 띄우지 않는다.
- 예정 삭제는 학생 일치·`plan:` ID·해당 월 지급권 없음·기존 유효 청구 없음이라는 화면 검사를 유지한다. 기본 항목은 남은 기본 옵션으로 교체하고 추가 항목은 `delete_planned_additional_student_billing_item`을 한 번 호출한다.
- 기본 응답의 월/옵션 수와 추가 등록/삭제 응답의 학생·옵션·계획·청구 월을 확인한다. 응답 유실/형식 불일치는 `BILL_PLAN_CHANGE_UNCONFIRMED`로 상태 조회를 안내한다. 직접 테이블 우회/자동 재시도는 없다.
- 확인된 변경 후 공통 통합 조회로 청구대상과 내역을 갱신한다. 갱신 실패는 `BILL_PLAN_REFRESH_FAILED`이며 저장을 재실행하지 않는다. 이전 요청으로 새 화면의 선택을 비우지 않는다.
- 과거 서버가 응답 필드를 생략하면 실제 변경이 되었어도 미확인으로 안내될 수 있다. 운영 예정 서버의 RPC 버전/응답 계약·다중 탭 동시성은 격리 검수가 필요하다.

## 현장 수납 탭

- 지점을 선택한 경우에만 `list_offline_payments(p_branch_id, p_status)`를 실행한다. 결제 순서와 필드는 유지하고 보호자의 삭제되지 않은 자녀명을 추가 조회해 중복 없이 연결한다. 하나라도 조회에 실패하면 부분 목록을 표시하지 않는다.
- 조회 요청 번호와 effect 정리로 지점·상태 변경/화면 이탈 후 오래된 응답을 무시한다. 현재 조회 실패는 이전 목록을 비우고 공통 오류로 표시한다.
- 수납 확정은 기존 결제 UUID로만 실행하며 신규 결제를 등록하지 않는다. 청구서 없는 앱 직접 결제는 서버의 `bill_status: null` 계약을 허용한다. 지급 확인이 없으면 별도 확인을 안내한다.
- 예정/수납 완료 취소는 기존 `cancel_offline_payment`를 한 번 호출한다. 서버의 `status: cancelled` 또는 `already_cancelled: true` 응답을 확인한다. 기존 계약은 결제 ID를 반환하지 않으며, 반환되는 서버에서는 동일 ID인지 검사한다.
- 완료 취소의 사용 여부 검사·미사용 이용권 회수·예약/청구 상태 변경은 서버의 기존 규칙을 유지한다. 장부 취소는 실제 현금 반환이나 PG 환불이 아니므로 별도 환불 확인을 안내한다.
- 확정과 취소는 한 잠금을 공유한다. 확인 창 전 중복 요청을 차단하고 처리 중 모든 행의 쓰기 버튼을 비활성화한다. 작업 후 지점/상태가 바뀌었으면 이전 조회를 실행하지 않는다.
- 완료/취소 후 조회 실패는 `OFFLINE_PAYMENT_REFRESH_FAILED`로 구분한다. 응답 미확인 시 자동 반복/직접 테이블 우회 없이 기존 결제·청구·이용권을 확인한다.
- 보호자 자녀의 대량 조회/행 제한·RPC 목록의 전체 규모·다중 기기 동시성은 별도 검토 대상이다. 이번 분리는 페이지네이션이나 서버 권한 검증을 대체하지 않는다.

## 수기 수납 등록·확정

- `schedule_offline_payment`에 청구서 ID·원 단위 정수 금액·기존 결제 수단 매핑·선택 날짜 한국시간 정오·메모를 전달한다. UUID, 양의 정수 및 DB integer 상한, 유효 날짜, 수단과 처리 방식을 먼저 검사한다.
- `success: true`와 결제 UUID를 확인한 다음에만 즉시 수납의 `confirm_offline_payment`를 실행한다. 예정 등록 방식이면 확정 호출하지 않는다. 자동 재시도나 직접 테이블 우회는 없다.
- 등록 응답 유실은 등록 실패 확정이 아니다. `PAYMENT_SAVE_FAILED`에서 폼을 닫고 기존 내역 확인을 안내한다. 권한/입력 오류는 폼을 유지한다.
- 등록 확인 후 확정 오류·응답 유실은 결제 UUID를 보존한 `confirmation-unconfirmed` 결과다. `PAYMENT_CONFIRM_PENDING`과 확인 가능한 권한/배포 오류를 구분해 안내한다. 새 결제 등록으로 해결하지 않는다.
- 부분 수납은 전액 수납이 아니므로 이용권 미지급 경고를 표시하지 않는다. 전액 수납의 지급 확인이 없거나 이미 수납된 응답이 지급 상태를 생략하면 `PAYMENT_PACKAGE_PENDING`으로 지급 내역 확인을 안내한다.
- 화면의 공통 잠금으로 중복 제출과 처리 중 다른 청구서 폼 열기를 막는다. 화면 전환 후 오래된 결과가 새 폼을 닫거나 목록을 덮어쓰지 않도록 한다.
- 처리 후 목록 갱신 실패는 `PAYMENT_REFRESH_FAILED`로 구분하며, 로그에는 가능한 결제 UUID만 공통 허용 필드로 기록한다.
- 예정 등록과 확정은 서로 다른 서버 트랜잭션이다. 다중 기기 멱등성·실제 서버 지급 규칙·RLS는 별도 검수가 필요하다. 이 기능은 장부 기록/이용권 처리이며 PG 결제나 현금 이체를 실행하지 않는다.

## 앱 등록·납부 알림 요청

- `send-academy-bills`에는 웹 청구서 ID, `send-payment-reminders`에는 앱 결제요청 ID를 보낸다. UUID 검증·중복 제거·최대 100건 제한을 적용하며 자동으로 여러 배치로 나누어 발송하지 않는다.
- 응답 집계 숫자를 그대로 믿지 않고 요청 ID별 결과를 확인한다. 누락·중복 결과, 잘못된 성공 형식은 미확인으로 분류한다. 다른 ID나 잘못된 배치 형식은 전체 요청 결과 미확인으로 안내한다. 형식이 맞는 개별 성공은 같은 배치의 실패/미확인과 구분한다.
- 서버 오류·경고 원문을 화면이나 서비스 결과에 넣지 않는다. 공통 코드만 해석하고 코드 없는 항목은 도메인 공통 안내를 사용한다.
- 청구서 신규/기존 등록은 휴대폰 푸시 도착을 의미하지 않는다. 현재 청구서 Edge 응답은 알림함/푸시 실패를 모두 반환하지 않아 클라이언트에서 그 성공을 보장할 수 없다.
- 납부 알림은 서버의 성공 항목을 알림함·이력 저장 확인으로 표시하고 `push_sent` 여부를 별도 집계한다. 푸시 접수도 실제 기기 수신 보장은 아니다. 실패 항목도 알림 저장 이후 이력 갱신이 실패한 경우가 있어 반복 발송 전 이력을 확인한다.
- 완료한 요청은 공통 갱신 경로로 목록을 재조회하며 갱신 오류는 `BILL_DELIVERY_REFRESH_FAILED`로 구분한다. 청구서 선택은 같은 화면의 확인된 ID만 해제한다. 화면 전환 이후 새 선택은 바꾸지 않는다.
- 앱·웹 클라이언트 코드만 정리했다. 서버 함수의 원시 로그, 알림 저장/발송/이력 갱신 간 원자성, 다중 탭·기기 동시 발송 방지는 별도 서버 검토 과제다. 이번에 서버 함수를 수정·배포하거나 실제 발송하지 않았다.

## 청구내역 조회 규칙

1. 선택 월의 `academy_bills`와 기존 학생·수업·옵션 관계를 읽는다. 특정 지점이면 지점 조건을 추가하고 `null` / `all`은 기존 전체 조회를 유지한다.
2. 연결된 결제요청 ID를 중복 제거한 후 100개 단위로 재발송 횟수/시각을 읽는다.
3. `withBillingReminder`로 재발송 필드만 합친다. 청구서 ID·금액·상태·지점은 결제요청의 값으로 덮어쓰지 않는다. 결제요청 ID를 청구서 삭제 ID로 사용해서는 안 된다.
4. 보관 처리된 학생의 청구서는 이력으로 유지한다. 보관되지 않은 학생의 삭제된 자녀/보호자 관계 제외 규칙은 기존과 같다.
5. 선택 월의 한국 시간 범위에서 앱 관리자 직접 청구(`issued_source = admin_app`)를 조회한다. 이미 웹 청구서와 연결된 결제요청은 직접 청구 목록에서 제외한다.
6. 어느 조회든 실패하면 부분 목록을 반환하지 않는다. 화면은 두 목록을 함께 지우고 공통 오류로 안내한다. 빈 결과도 빈 배열로 반영한다.

기존 학생 관계 필터, 월 기준, 정렬과 조회 범위는 유지했다. 서버 응답 행 제한과 전체 명부 페이지 조회는 이번 단계에서 확장하지 않았다. 대량 데이터가 자동으로 모두 조회된다고 가정하지 않는다.

## 자동 청구 설정 조회

- 특정 지점의 설정과 활성 대상 학생 ID를 읽는다. 전체 지점 선택은 DB 조회 없이 기존 비활성 기본값을 반환한다.
- 두 조회 중 하나라도 실패하면 오류로 처리한다. 이전 지점 설정이 늦게 도착해 새 지점의 화면을 덮어쓰지 않도록 요청 번호로 구분한다.
- 조회 실패 후 화면의 초기화된 표시값은 서버 설정 변경이 아니다. 서버에서 자동 청구가 꺼졌다고 해석하면 안 된다. 실제 설정은 재조회해야 한다.
- 조회 서비스는 설정을 수정하거나 발송하지 않는다. 설정/대상 학생 저장은 `billingAutomation.ts`로 분리했고 실제 예약 실행/발송 로직은 이번 단계에서 변경하지 않았다.

## 연결된 화면의 요청 수명

청구대상/청구내역은 같은 로딩 표시를 사용하므로 공유 요청 번호로 이전 작업의 결과와 로딩 해제를 무시한다. 탭·지점·월 변경 또는 화면 이탈 시 effect cleanup이 이전 요청을 무효화한다. 자동 청구 설정은 별도 요청 번호를 사용한다.

## 다음 단계

- 청구 삭제·무료 처리·발송, 월별 청구 계획 저장, 현장 수납 등 기존 쓰기 경로의 책임 분리.
- 격리 환경에서 실제 관계 조인·권한·대량 데이터와 사용자 화면 검수.

이번 정리만으로 수납 관리 전체가 리팩토링되거나 운영 검증된 것은 아니다.

## 청구대상 조회와 계산

조회 서비스는 학생·상품을 읽고, 앱 학생 ID로 기준 개정/월별 계획/수업 배정을 읽는다. 자녀 보유권과 보호자 공유 차량권, 옵션 정보, 기존 발행 청구를 읽은 뒤 `buildBillingTargets`에 전달한다. 일부 조회가 실패하면 상품 목록이나 학생 명부만 먼저 표시하지 않는다.

기존 관계 응답의 형태는 `BillingTargetReadSnapshot` 경계에서 받아 계산한다. 기존 `any` 기반 조인 해석을 무리하게 새 스키마로 바꾸지 않았으며, 생성 DB 타입 적용과 조인 배열/단일 객체의 추가 표준화는 후속 검토 대상이다.

유지한 주요 규칙:

- 활성 명부만 대상으로 하며 앱 자녀의 실제 보호자 ID를 우선한다. 수납 설정이 없는 학생도 명부에서 누락시키지 않는다.
- 일반 이용권 계획은 최신 기준 개정 월을 사용한다. 추적 개정이 없는 기존 데이터는 선택 월의 계획을 사용한다. 수업/추가 청구는 선택 월만 적용한다.
- 앱 보유권은 새 청구 지시가 아니다. 저장된 계획의 갱신 여부와 실제 지급 옵션의 불일치 판단에 사용한다. 명시적으로 비운 계획을 과거 보유권으로 되살리지 않는다.
- 공유 차량권은 보호자·지점·상품별로 합치고 대표 학생을 결정적으로 선택한다. 명시적 추가 청구는 합치지 않는다.
- 웹 전용 학생은 기존 활성 수업-요금제 연결을 사용한다.
- 발행 청구만 남은 경우 이력용 대상을 복원한다. 표시 금액은 기존 청구액이며 갱신 여부의 상품 비교는 카탈로그 가격을 유지한다. 청구 상태 우선순위는 납부 → 부분납부 → 미납이다.
- 선택 월의 기간 중복, 무기한 활성 이용권, 이전 월 단품/1회권 제외, GPS 보유권/선택 카탈로그 제외 범위를 기존과 같이 유지한다.

`userPackageId`는 모든 대상이 실제 앱 이용권이라는 뜻이 아니다.

| 값의 형태 | 의미 |
| --- | --- |
| 실제 보유권 ID | 갱신 상태 비교용 보유권/공유권 |
| `plan:...` | 월별/반복/추가 청구 계획에서 만든 대상 |
| `web:...` | 웹 학생의 수업-요금제 연결 대상 |
| `bill:...` | 발행 청구에서 복원한 이력용 대상 |

화면은 네 결과 목록을 한 번에 반영한다. 실제 청구 생성·발송·삭제는 여전히 별도 기존 경로이며, 이 계산 함수 실행만으로는 돈이나 DB 상태가 바뀌지 않는다.

## 자동 청구 설정·대상 저장

- 지점 설정은 `academy_billing_automation_settings`의 기존 `branch_id` 충돌 키와 `billing_day: 1`을 유지한다. 대상 학생은 `academy_billing_automation_targets`의 `branch_id,student_id` 키로 한 번에 저장한다.
- 각 저장은 `auth.getUser()`의 오류/로그인 여부를 검사하고 확인된 사용자 ID와 같은 시각을 기록한다. 실제 쓰기 권한은 기존 서버 RLS가 결정한다. 클라이언트의 지점 검사만으로 권한을 보장하지 않는다.
- 대상 학생 ID는 중복 제거한다. 선택 지점/ID가 없으면 쓰지 않는다. 저장 후 반환된 지점·활성값·대상 ID가 요청과 일치해야 화면을 성공 값으로 바꾼다.
- 설정과 대상 학생 저장은 같은 즉시 잠금을 공유한다. 이전 설정 조회 응답을 무효화하고, 지점 변경/화면 이탈 이후 늦은 저장 응답은 새 지점의 표시값에 반영하지 않는다.
- 현재 지점의 조회가 완료되어야 변경할 수 있다. 조회 실패 또는 저장 응답 미확인 시에는 변경을 막고 페이지 새로고침 등으로 상태를 먼저 확인하도록 안내한다. 응답 유실은 저장 실패 확정이 아니며 자동 재시도하지 않는다.
- 개별/전체 대상 선택 범위와 활성화 안내는 유지했다. 이 서비스는 청구서 생성/발송을 직접 호출하지 않지만 실제 운영에서 활성화된 설정은 기존 스케줄러가 사용할 수 있다. 격리 검수 환경 외에서 임의로 켜지 않는다.
- 실제 RLS의 upsert 후 select 권한, 많은 대상에 대한 반환 행 제한, 여러 탭/기기의 동시 변경은 추가 검수가 필요하다.

## 청구 생성

결제 탭 조회의 상세 계약과 미해결 제한은 아래 ‘결제 내역 조회·표시’를 참고한다.

- 기존 `allocateDiscountedBillAmounts`를 그대로 사용해 합계에서 할인 후 원 단위 잔여분을 나눈다. 직접 입력 금액의 키·문자 정리·0원/증액 처리와 할인 저장 필드, 기존 메모 형식도 유지했다.
- `create_manual_student_bill`의 학생/계획/옵션/월/금액/할인/메모 매개변수는 변경하지 않았다. 새 DB 함수, 발송 또는 결제 호출을 추가하지 않는다.
- 성공 응답은 `success: true`, boolean `created`, UUID 형태 `bill_id`를 확인한다. `created: false`는 기존 청구로 집계한다. 로컬 앱 마이그레이션에 이 응답 계약과 학생/월/옵션 중복 검사·잠금이 있지만 실제 운영 배포 일치는 별도 검수가 필요하다.
- 명시적 RPC 오류는 공통 코드로 정규화해 해당 건 실패로 집계하고 다른 독립 대상 처리를 유지한다. 옵션 누락은 요청하지 않는다. 요청 예외나 응답 형식 미확인은 실패 확정으로 세지 않고 나머지 실행을 중단한다.
- 다건 작업 전체는 원자적이지 않다. 이미 성공한 청구는 이후 실패/응답 유실로 되돌아가지 않는다. 생성/기존/실패/미확인/미실행 수를 구분하고 자동 재시도하지 않는다.
- 해당 화면에 머문 경우 처리 후 선택을 해제하고 청구내역 탭으로 이동한다. 기존 탭/월 effect가 새 월의 내역을 조회하므로 이전 월을 캡처한 조회를 직접 실행하지 않는다. 중간에 사용자가 화면을 바꾸면 새 화면의 선택/할인/월을 덮어쓰지 않고 결과만 안내한다.
- 부분 결과에서는 할인 입력을 유지한다. 모든 결과를 확인한 경우에만 할인 입력을 초기화한다. 재실행 전 내역 조회와 서버 중복 방지 확인이 필요하다.
- 로그에는 공통 코드·허용된 작업명·반환된 거래 UUID만 사용한다. 원시 RPC 응답이나 요청의 이름/금액/메모/토큰을 로그에 쓰지 않는다.

## 결제 내역 조회·표시

- 결제는 기존 payer 외래키 명시 조인과 최신순, 선택 지점 필터를 유지한다. 관계별 조회도 기존 필드/필터를 유지한다. 최고관리자만 전체 지점(null) 조회를 요청할 수 있으며 지점 없는 일반 계정은 화면에서 차단한다. 실제 접근 제어는 서버 RLS 검수가 필요하다.
- 결제·연결 이용권·자녀·원생·상품/옵션·문자 충전 로그 응답을 모두 검사한다. 어느 하나라도 실패하거나 배열 응답이 아니면 부분 결과를 정상 목록처럼 반환하지 않는다. 서비스가 오류를 정규화하고 화면은 공통 핸들러를 사용한다.
- 연결 이용권이 없으면 기존 `order_items`의 상품/옵션 ID로 현재 카탈로그의 표시명을 복구한다. 이는 판매 당시 불변 가격/상품 증거가 아니며 quantity 확장도 기존처럼 하지 않는다. 카탈로그가 삭제됐다면 복구하지 못할 수 있다.
- 자녀 이름 중복 제거, payer 단일/배열 관계 처리, 충전 거래번호 분류를 유지한다. 기존 select에 memo/source는 없어 실제 조회의 해당 분기에는 값이 없으며, 이번에 새 DB 컬럼을 가정해 select를 확대하지 않았다.
- 월은 한국시간으로 표시 필터링하며, 다른 달의 환불 행도 참고할 수 있도록 DB 쿼리에 월 제한을 새로 추가하지 않는다. 환불액은 기존 `_REFUND`/`-REFUND` 거래번호 규칙이며 PG 원장 검증이나 누적 환불의 최종 보장은 아니다.
- 합계는 기존 paid/success 상태 금액 합산이다. 순매출·수수료·실제 정산 보고서로 해석하면 안 된다. 검색/상태 선택은 목록에만 적용하고 통계는 선택 월 기준을 유지한다.
- 요청 번호가 오래된 성공/실패는 목록·오류·로딩을 바꾸지 않는다. 지점/월/탭 변경·화면 이탈 시 이전 요청을 무효화한다. 월 변경 시 새 조회도 시작해 무효화된 요청만 남는 흐름을 방지했다. 취소 후 조회 실패는 기존 `PAYMENT_CANCEL_REFRESH_FAILED`로 구분한다.
- **미해결 제한**: 기존 조회는 DB 행 수 제한의 영향을 받을 수 있고 ID 목록 분할/서버 페이지 순회는 아직 없다. 반환된 범위를 전체 거래 원장으로 보장하지 않는다. 자녀/원생/충전 로그의 실제 RLS 범위와 대량 자료, 브라우저 동작은 격리 검수가 필요하다.
- `npm run test:payment-history`는 실제 DB·결제 연결 없는 조회/계산/화면 요청 수명/오류 문구 동기화 테스트다.
