# 학생관리 기능 경계

## 파일 역할

- `types.ts`: 학생 목록, 미등록 회원, 수업, 상품 옵션, 탈퇴 이력의 화면 데이터 타입.
- `api/studentData.ts`: 재원생 목록과 편집에 필요한 선택 목록 조회 전용. Supabase client와 활성 수업 조회 함수를 주입하므로 외부 연결 없이 테스트할 수 있다.
- `api/withdrawalData.ts`: 저장된 탈퇴/환불 정보 조회와 과거 앱 계정 탈퇴의 조회용 행 복원. 순수 변환 함수 `buildWithdrawalRecords`와 DB 조회 함수 `loadWithdrawalData`를 구분한다.
- `api/studentDetailData.ts`: 상세 편집에 필요한 정류장·이용권·월별 계획·청구 연결 정보를 읽고 화면 값으로 계산한다. DB client와 날짜 기준을 전달받으며 저장하지 않는다.
- `api/studentSave.ts`: 학생 기본 정보 → 웹 수업 배정 또는 앱 정류장/수업·청구 계획 저장 순서를 관리한다. 보호자 전화번호 조회도 이 서비스에서 오류를 검사한다.
- `api/studentBilling.ts`: 추가 청구 계획과 실제 지급 이용권 기준 계획 정정을 각각 기존 RPC 한 번으로 처리한다.
- `api/studentLifecycle.ts`: 기존 보관 RPC를 통한 재원 명부 제외와 탈퇴 이력의 환불 정산 기록 수정을 담당한다. 실결제 환불은 실행하지 않는다.
- 화면 연결: `src/pages/admin/students/views/AdminStudentTab.tsx`의 `loadData`, `loadWithdrawals`.
- 테스트: `tests/studentData.test.mjs`, `tests/withdrawalData.test.mjs`, `tests/studentDetailData.test.mjs`, `tests/studentSave.test.mjs`, `tests/studentBilling.test.mjs`, `tests/studentLifecycle.test.mjs`. 실행 명령 `npm run test:students`.

## 조회 순서와 기존 규칙

1. 지점별 수업과 활성 상품 옵션을 읽는다. `null` / `all`은 기존 전체 지점 조회를 유지하며, 실제 접근 범위는 서버 권한에 따른다.
2. 보관 처리되지 않은 웹 학생, 삭제되지 않은 앱 자녀, 삭제되지 않은 회원을 조회한다.
3. 학생 ID로 웹 수업 배정과 해당 월의 `planned` / `applied` 수업 계획을 읽는다. 기본 학생 쿼리에 수업 관계를 중첩하지 않는다.
4. 삭제된 자녀·보호자의 학생은 제외하고, 앱 자녀 중 웹 명부에 없는 자녀를 조회용 학생 행으로 합친다. 이 과정은 DB에 학생을 생성하지 않는다.
5. 자녀/학생이 없는 일반 회원은 학생 명부와 별도의 미등록 회원 목록에 둔다.
6. 앱의 활성 수업 배정과 활성 이용권을 조회한다. 연결 학생은 월별 수업 계획을 우선하고, 계획이 없으면 앱 수업 배정을 사용한다. 수동 등록 학생은 웹 수업 배정을 유지한다.
7. 최신순으로 읽은 이용권에서 만료되지 않은 첫 이용권을 연결한다. 만료 판단의 UTC 날짜 방식은 이번 단계에서 변경하지 않았다.

실패한 조회가 하나라도 있으면 전체 결과를 반환하지 않는다. 화면에서 이전 목록을 지우고 공통 오류로 안내한다.
현재 월은 호출 측에서 전달한다. 원래 화면의 `currentBillMonth()`가 날짜 기준이므로 임의로 UTC 월로 바꾸지 않는다.

## Excel 가져오기·양식

등록 양식 생성은 `files/studentTemplate.ts`로 분리했다. 기존 15개 열 순서·시트명·너비와 파일명을 유지하며 샘플 학생 데이터를 넣지 않는다. 다운로드 처리는 공통 `src/lib/excelDownload.ts`를 사용해 임시 링크와 object URL을 정리한다. `npm run test:excel`로 생성/읽기/행 변환을 검증한다.

### 학생 Excel 읽기·행 변환

- `files/studentImport.ts`: `file.arrayBuffer()`로 파일을 읽고 첫 시트의 첫 행을 헤더로 제외한 뒤 15개 셀의 `text`를 전달한다. 파일 읽기/파싱 실패는 학생 등록 시작 전 오류로 안내한다.
- `model/studentImport.ts`: 외부 연결 없는 행 변환. 필수 이름/출결번호가 없는 행 제외, 공백 제거, 연락처 숫자 추출, 기존 날짜 규칙, 납부 주기/수납일 기본값과 학생-배정 인덱스를 유지한다.
- 날짜는 기존처럼 숫자 8자리 또는 하이픈 포함 문자열을 사용한다. 달력상 유효성·Excel 날짜 일련번호·Date 셀의 표준화를 새로 구현한 것은 아니다. 출결번호가 숫자 셀이면 이미 유실된 선행 0은 복원하지 않는다.
- 화면의 공통 저장 잠금으로 파일 읽기부터 중복 업로드와 다른 학생 쓰기를 막는다. 읽는 동안 조회/지점이 바뀌면 DB 쓰기를 시작하지 않는다. 쓰기를 시작한 뒤의 서버 요청을 취소하는 기능은 아니다.
- `model/studentImportPlan.ts`에서 파일 전체의 저장 계획을 먼저 만든다. 명시적 지점, 파일 내 출결번호 중복, 유효한 달력 날짜, 지점 내 수업/요금제의 정확한 단일 매칭을 요구한다. GPS 옵션은 배정하지 않는다. 수업명 생략은 이용권 단독 배정을 유지한다.
- `api/studentImport.ts`는 중복 출결번호 존재 여부를 지점별 100개 묶음으로 읽고 보호자 후보를 모두 확인한 뒤 쓰기를 시작한다. 보관 학생도 중복 검사에 포함한다. 보호자 후보가 여러 명이면 임의로 한 계정을 고르지 않는다. 유효한 후보가 없으면 기존처럼 미연결을 유지한다.
- 전체 지점에서 첫 지점을 선택하거나 미일치 요금제를 첫 옵션으로 대체하던 동작은 제거했다. 같은 이름의 수업이 여러 시간대로 존재하는 경우에도 임의 배정하지 않고 사전 검증 오류를 안내한다. 현재 양식은 이름만 있으므로 구분 가능한 이름을 정리하거나 후속 ID 기반 양식을 설계해야 한다.
- 학생 insert 후 같은 학생·클래스·옵션의 배정 반환 행까지 확인한다. 반환 행을 조회할 수 있는 RLS 권한이 필요하다. 확인된 학생/배정 수, 미실행 행, 상태 확인 필요 여부를 별도로 반환하고 실패 즉시 나머지 쓰기를 중단한다.
- 지점/조회가 바뀌면 다음 학생을 시작하지 않는다. 이미 학생을 저장한 행은 배정 단계까지 마친다. 처리된 행을 자동 삭제하거나 파일 전체를 다시 올리지 않는다.
- 파일 전체 트랜잭션·서버 멱등성·자동 재개·동시 요청의 중복 방지는 아직 없다. 사전 중복 조회와 실제 insert 사이에 경쟁이 있을 수 있다. 명단/RLS 가시성 밖 데이터나 다른 클라이언트까지 검사했다는 뜻은 아니다. 서버 제약·원자적 RPC는 별도 설계/마이그레이션 검토 대상이다.

이 경로들은 여전히 기존 화면 파일에 있다. 이번 목록 조회 분리만으로 학생관리 전체의 정리·보안 검증이 완료된 것은 아니다.
조회 서비스에는 쓰기를 추가하지 않는다. 저장 서비스는 기존 쓰기 경로만 사용하며, 신규 RPC·자동 재시도·RPC 실패 후 직접 테이블 우회·알림/실결제 호출을 추가하지 않는다.

## 상세 편집 조회 규칙

- 앱 자녀 연결이 없는 학생은 원래처럼 원격 상세 조회 없이 빈 수업/이용권 값으로 편집을 시작한다. 웹 수업 배정은 화면에서 별도로 유지한다.
- 연결 학생은 활성 정류장과 개인 설정을 읽은 뒤, 보유 이용권·이번/다음/지난달 계획·이번/지난달 청구·반복 청구 기준 개정 이력을 읽는다. 10개 조회 모두 성공해야 상세 편집을 연다.
- 이번 달 이용권은 명시적 반복 기준 개정 → 이번 달 계획 → 유효 청구 → 지난달 계획 → 지난달 청구 → 보유 이용권 순서를 유지한다. 명시적인 빈 개정은 보유 이용권으로 채우지 않는다.
- 다음 달 이용권은 저장된 다음 달 계획 → 반복 기준 개정 → 기존 값 미리보기 순서를 유지한다. 청구 주기·결제일과 중복 옵션 제거도 기존 방식이다.
- 취소/무효/삭제 청구 제외, 이번 달 발급 이용권·적용된 계획·발행 청구의 잠금 계산, 계획/실제 이용권 불일치 계산은 이번 단계에서 정책을 바꾸지 않았다.
- 날짜 기준은 화면에서 전달한다. 기존 로컬 월과 UTC 일자 구분을 유지한다.
- 화면은 조회 완료 전에 폼 값을 바꾸지 않는다. 닫기·지점 변경·화면 이탈 시 요청을 무효화하고, 이전 학생의 늦은 성공/실패 응답을 무시한다.
- 신규 등록 시 이전 편집의 청구 잠금과 추가 옵션 값도 초기화한다. 추가 청구 함수는 기존 경로에 남아 있다.

## 학생 등록·수정 저장의 경계

1. 화면에서 기존 필수값/중복 수업·이용권 검증과 앱 연결 학생 확인 창을 유지한다. `saveInFlight`로 같은 화면의 중복 실행을 막는다.
2. 앱 연결 학생의 보호자는 자녀 소유권을 우선한다. 웹 학생은 기존 전화번호 검색을 사용하되 조회 오류를 미연결로 취급하지 않는다. Excel 업로드도 동일 조회 헬퍼를 사용한다.
3. `academy_students`를 등록/수정한다. 앱 목록의 `child-...` 가상 ID는 실제 연결 행을 조회한 뒤 해당 행을 수정하거나 생성한다. 수정은 `select('id').single()`로 실제 반영 행을 확인한다.
4. 웹 학생은 기존 수업 배정 삭제/등록 경로를 유지한다. 앱 학생은 정류장 설정 후 기존 `save_student_schedule_and_billing_all_months` RPC를 한 번 호출한다.
5. 학생 기본 정보 저장 이후 수업 배정 실패, 정류장 실패, 수업·청구 계획 결과 미확인을 각각 다른 공통 코드로 안내한다. 부분 성공/응답 미확인 시에는 편집창을 닫고 목록을 다시 조회해 재등록을 유도하지 않는다.

전체 저장은 하나의 트랜잭션이 아니다. 기본 정보·웹 배정·정류장 저장은 후속 RPC 실패로 되돌아가지 않으며, 웹 배정 삭제 후 등록 실패도 가능하다. 새 DB 마이그레이션 없이 기존 순서를 보존한 것이므로 원자성 문제를 해결했다고 보면 안 된다.
네트워크 응답 유실은 저장 실패 확정이 아니다. 서비스는 자동 재시도하지 않으며 운영자는 목록/상세/계획 상태를 확인한 후 필요한 항목만 수정해야 한다. 가상 학생 생성과 여러 브라우저 간 동시 저장의 멱등성은 서버 트랜잭션 설계의 후속 검토 대상이다.

## 추가 청구·청구 계획 정정

- 추가 청구: `add_current_month_student_additional_billing_plan(p_student_id, p_package_option_id)`.
- 계획 정정: `correct_billing_plan_to_owned_package(p_plan_id, p_user_package_id)`.
- 확인 창, 중복 옵션 사전 검사, RPC 이름과 매개변수는 유지한다. 금액 계산·실결제·앱 이용권 변경을 위한 새 호출을 추가하지 않았다.
- 같은 화면에서는 두 작업이 `billingMutationInFlight`를 공유한다. 학생 저장/탈퇴 처리와의 동시 실행도 막는다. 여러 탭·기기에서의 동시 요청은 서버 검증이 별도로 필요하다.
- 성공한 RPC 뒤에는 최신 명부의 학생과 최신 상품 옵션으로 상세 조회를 다시 실행한다. 이전 React state의 학생 객체·상품 목록을 재사용하지 않는다.
- RPC 응답 미확인과 RPC 성공 후 화면 새로고침 실패를 다른 코드로 안내한다. 결과 미확인/갱신 실패 시 해당 편집창을 닫고 상태 재조회를 요청한다. RPC를 자동 반복하거나 테이블 쓰기로 우회하지 않는다.
- `loadData(false, isCurrent)`와 `openModal(student, { reportError: false, packageOptions })`는 저장 이후 갱신용이다. 이 경로에서는 조회 오류를 상위 호출자에게 전달해 저장 성공 여부와 구분한 안내를 한 번만 표시한다. 일반 조회는 기존 자체 오류 안내를 유지한다.
- 지점/편집 대상이 바뀌면 오래된 저장 응답으로 이전 창을 다시 열지 않는다. 저장 자체는 취소되는 것이 아니므로 실제 내역은 다시 조회해야 한다.

## 재원 명부 제외·환불 정산 기록

- 명부 제외는 기존 `archive_academy_student` RPC만 사용한다. 일반 ID와 앱 자녀의 `child-...` 조회 ID를 원래 매개변수로 변환하고 `archived` / `already_archived`만 처리 확인으로 인정한다. 물리 삭제로 우회하지 않는다.
- 화면의 사유/이름 확인 절차와 기존 안내는 유지했다. 두 명부 제외 진입점은 `archiveInFlight`를 공유하고 학생 저장·청구 계획·환불 기록 작업과의 충돌을 차단한다.
- 환불 정산 저장은 `user_withdrawals`의 `refund_status`, `refund_amount`, `refund_memo`, `refunded_at` 수정뿐이다. PG 취소·계좌 송금·환불 지급 호출은 없다.
- 실제 저장 행의 ID가 반환되어야 저장을 확인한다. 조회용 복원 행은 수정하지 않으며 음수·소수·비정상 숫자·잘못된 상태를 서버 요청 전에 차단한다. 원래처럼 완료 상태는 현재 시각을 기록하고 대기/해당 없음은 완료 시각을 지운다. 환불액을 실결제액 기준으로 자동 조정하는 정책은 추가하지 않았다.
- 응답 미확인, 권한 오류, 저장 확인 후 목록 조회 실패를 구분한다. 미확인 결과에서는 편집창을 닫고 내역 재조회를 안내하며 자동 재시도하지 않는다.
- 저장 후 명부와 탈퇴 이력을 함께 재조회한다. 지점 변경/화면 이탈은 이전 요청의 화면 반영만 막으며, 이미 전송된 서버 처리를 취소하지 않는다.
- 전체 다중 탭 동시성·실제 RLS/반환 행 조회 권한·운영 RPC 배포 상태는 별도 검수가 필요하다. 이번 단계에서 DB 정책이나 SQL을 변경하지 않았다.

## 탈퇴 이력 조회 규칙

- `user_withdrawals`, 삭제 상태인 `users`, 지점별 `academy_students`를 병렬 조회한다. 하나라도 실패하면 부분 목록을 반환하지 않는다.
- 저장된 탈퇴 이력의 환불 금액·상태·메모는 변환하지 않는다.
- 계정 단위의 저장 이력이 있으면 같은 계정의 복원 행을 추가하지 않는다. 자녀 단위의 저장 이력은 해당 자녀의 복원 행만 제외한다.
- 익명화 이메일 `deleted_<timestamp>@unknown.com`의 시간을 기존처럼 사용한다. 패턴이 없으면 회원의 `created_at`을 사용한다. 형식은 맞지만 시간 값이 잘못된 경우 기존과 같이 조회 오류가 발생하며, DB를 임의 보정하지 않는다.
- 연결 학생이 있으면 학생별 행을 만들고, 표시할 연결 학생이 없으면 계정 단위의 익명 행을 만든다. 저장 이력이 모든 자녀를 포함해도 별도 계정 이력이 없으면 계정 단위 행이 생기는 기존 규칙을 유지한다.
- 복원 행은 `is_inferred: true`, `refund_status: 'none'`이다. 실제 탈퇴 이력을 생성하거나 환불을 실행하지 않는다.
- 저장/복원 행을 함께 최신순으로 정렬한다. 화면은 재원생 조회와 별도의 요청 번호를 사용해 오래된 응답을 무시한다.
